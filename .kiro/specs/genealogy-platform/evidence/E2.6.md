## Decisions

- **Single KMS application contract.** Application code binds to
  `com.genealogy.platform.kms.KmsProvider`; the platform selects
  AWS KMS (SaaS) or Vault transit (on-prem) via the per-env
  values file. Domain code never branches on the provider.
- **AWS KMS for SaaS, Vault transit for on-prem.** Per
  `tasks.md` E2.6 + `design.md` §13, SaaS cloud KMS wraps the
  master KEK via IRSA / pod identity; on-prem uses Vault transit
  against a customer-managed bootstrap Vault cluster. No literal
  AWS key is ever stored in Git / Helm values / image / log.
- **Kubernetes auth is canonical workload identity.** Vault
  Agent Injector uses the projected Kubernetes SA token. Keycloak
  JWT is reserved for human operators; GitHub Actions AppRole is
  reserved for CI / GitOps. `userpass`, `ldap`, `cert` are
  forbidden because credential storage belongs to Keycloak.
- **Deny-all default + per-workload ACL.** A workload with no
  explicit policy gets no access. Every policy is path-scoped to
  `secret/data/<workload-class>/...`; `root` / `sudo` capability
  is forbidden.
- **One key per data class.** Every class in
  `privacy-and-legal-gate.md` §5 has a dedicated KMS key; a reused
  `keyId` is a lint violation. `GENETIC.RAW` has its own 30-day
  rotation key + emergency revoke contract (E10.5).
- **Raft integrated storage.** No Consul dependency. 3 replicas
  by default (5 SaaS, 3 on-prem, 1 dev) with encrypted
  `gp-data-ssd` PVC.
- **Vault audit via OTel, not file audit.** Raw Vault request
  payload is never persisted to the StatefulSet volume; the OTel
  log pipeline (E2.10) redacts PII / DNA per
  `privacy-and-legal-gate.md` §11.
- **Helm-hook Job for bootstrap.** `vault-bootstrap` runs on every
  `helm upgrade` (`pre-install,pre-upgrade`) and is idempotent:
  initialise if needed, unseal, enable auth methods, write
  policies, mount KV v2.

## Security and privacy

- **Tenant isolation: N/A at the Vault layer.** Tenant isolation
  is enforced by service-side tenant predicates + PostgreSQL RLS
  + OpenFGA / ABAC. Vault policies are workload-scoped, not
  tenant-scoped; a workload gets only its own secret path. Raw
  tenant IDs never appear in Vault paths — per-workload aliases
  + pseudonymous labels only.
- **Authorization / ABAC: PASS — boundary enforced.** Vault
  decides credential scope only. Domain authorization (living /
  DNA / consent) stays in the destination service via OpenFGA +
  ABAC; the contract stub explicitly forbids business
  authorization in Vault.
- **Secret / PII / DNA leakage: PASS.** The deep linter rejects
  literal `password`, `apiKey`, `token`, `private_key`,
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` values. No raw DNA /
  PII / secret payload is stored in Git / Helm values / image /
  logs / Temporal payload. The local dev root token is explicitly
  dev-only and never used by the SaaS / on-prem profiles.
- **KMS key isolation: PASS.** 11 data classes have 11 distinct
  key IDs; the linter rejects reuse. `GENETIC.RAW` uses a
  dedicated 30-day rotation key + emergency-revoke method.
- **Short-lived credentials: PASS.** Default lease TTL 30m, max
  24h; GitHub Actions AppRole secret-id TTL 90d; Vault Agent
  revokes token on pod shutdown.
- **Default deny: PASS.** `default` policy grants only `deny`; no
  policy grants `root` / `sudo`; forbidden auth methods are not
  enabled.
- **Transport security: PASS.** Vault listener pins TLS 1.3;
  Istio adds strict mTLS + SPIFFE identity; NetworkPolicy denies
  ingress / egress by default.
- **License discipline: PASS.** HashiCorp Vault 1.17.x is MPL-2.0;
  Vault K8s is MPL-2.0. No AGPL dependency introduced.

  token into a short-lived Kubernetes Secret for the injector.
  E14.1 owns the production procedure that moves this material to
  a KMS-backed bootstrap store and rotates it after the first
  install.
