### `services/tenant-service/src/main/resources/db/migration/V2__tenant_aggregate.sql` (new)

Schema + role + RLS migration applied by Flyway after `V1__baseline_schema.sql`:

- **Schema**: `tenant_service` (already created by V1; V2 adds tables).
- **Tables** (5):
  - `tenants` — `id TEXT PK`, `slug` (regex `^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$`),
    `display_name` 1–120, `plan` enum (`FREE`/`FAMILY`/`PRO`/`ENTERPRISE`),
    `status` enum (`ACTIVE`/`SUSPENDED`/`DELETED`), `tenant_id = id` (self
    by design — tenant IS its own scope root), `version BIGINT`,
    `etag TEXT DEFAULT '"v1"'`, `created_at`/`updated_at`/`suspended_at`
    /`deleted_at`, plus consistency CHECKs (suspended_at IS NOT NULL ⇔
    status = SUSPENDED, deleted_at IS NOT NULL ⇔ status = DELETED).
    UNIQUE on `slug` (global — slugs are universal per ADR-E0.5-02 schema
    topology).
  - `memberships` — `id TEXT PK`, `tenant_id` + `user_id` (opaque Keycloak
    `sub`), `person_id` nullable (wired by E4.x verification gate per R3),
    `role` enum (`OWNER`/`ADMIN`/`MEMBER`/`AUDITOR`/`BILLING_ADMIN`),
    `status` enum (`INVITED`/`ACTIVE`/`SUSPENDED`/`REVOKED`), status
    consistency CHECK, UNIQUE on `(tenant_id, user_id)` (one membership
    per user per tenant).
  - `invitations` — `id`, `tenant_id`, `email`, `role`, `token_hash`,
    `idempotency_key`, `invited_by_user_id`, `expires_at`, accepted/revoked
    timestamps, UNIQUE on `(tenant_id, idempotency_key)`.
  - `entitlements` — PK `tenant_id`, `plan`, `member_limit`,
    `tree_limit`, `storage_limit_mb`, `retention_days`, all `>= 0`,
    `billing_external_id`.
  - `outbox_events` — `id`, `tenant_id`, `aggregate_type` enum
    (`tenant`/`membership`/`invitation`/`entitlement`), `aggregate_id`,
    `event_type`, `payload BYTEA` (Avro), `schema_id`,
    `correlation_id`, `trace_id`, `dispatched_at`, `dispatch_attempts`,
    `last_dispatch_error`. Writer lands in E3.2c (per scope guard).
- **Roles** (ADR-E0.5-02 split):
  - `tenant_service_owner` — DDL + DML inside `tenant_service`. Created
    out-of-band by the ADR-E0.5-02 runbook (Testcontainers fixture uses
    the superuser `tenant_service_owner`).
  - `tenant_service_app` — DML only, `NOLOGIN`, no DDL privilege.
    Granted `SELECT/INSERT/UPDATE/DELETE` on all tables in the schema
    plus sequence privileges. Runtime pattern: connection pool user
    issues `SET LOCAL ROLE tenant_service_app` per transaction
    (mirrored in `RlsNegativeIT#newRuntimeSession`).
- **Helper**: `tenant_service.current_tenant_id()` — `STABLE SQL` function
  returning `NULLIF(current_setting('app.tenant_id', true), '')`. Returning
  NULL when unset is the defense-in-depth branch (policy matches no rows).
- **RLS**:
  - `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` on every
    tenant-scoped table. FORCE is critical: without it the table owner
    bypasses RLS — a tenant-escape vector.
  - Policy `tenant_isolation` on each table:
    ```sql
    USING (tenant_id = tenant_service.current_tenant_id())
    WITH CHECK (tenant_id = tenant_service.current_tenant_id())
    ```
  - Same policy reused across all 5 tables; dropping the policy is
    `DROP POLICY IF EXISTS tenant_isolation` so a partial re-run is
    safe on a developer machine.

### `services/tenant-service/src/integrationTest/java/com/genealogy/platform/services/tenant/RlsNegativeIT.java` (new)

E3.2a Definition-of-Done gate. 7 test methods:

1. `migrationsApply` — V1 + V2 land on a fresh Postgres, five tables exist.
2. `rlsEnabledAndForced` — every tenant-scoped table has
   `relrowsecurity = true` AND `relforcerowsecurity = true`.
3. `runtimeRoleScopedToTenant` — `SET LOCAL ROLE tenant_service_app`
   + `SET LOCAL app.tenant_id = 'tenant-aaaa-1111'` sees only
   `tenant-aaaa-1111` rows.
4. `crossTenantSelectReturnsZeroRows` — same session as `tenant-bbbb`
   SELECTing for `tenant-aaaa-1111` returns `count(*)=0`.
5. `unsetTenantIdReturnsZeroRows` — `app.tenant_id` unset ⇒
   `count(*)=0` (defense-in-depth).
6. `crossTenantMembershipSelectReturnsZeroRows` — cross-tenant membership
   read blocked.
7. `crossTenantInsertRejected` — `WITH CHECK` blocks an INSERT whose
   `tenant_id` does not match `app.tenant_id`.
8. `runtimeRoleHasNoDdlPrivilege` — `tenant_service_app` cannot `CREATE
   TABLE`.

The IT starts its own Testcontainers container (does not reuse the shared
`PostgresFixture`) because the shared fixture connects as a superuser and
would bypass `FORCE ROW LEVEL SECURITY`. The Testcontainers owner is
granted membership in `tenant_service_app` so the IT can exercise
`SET LOCAL ROLE` — the same pattern the production connection pool will
use (low-privilege login user issues `SET LOCAL ROLE` per transaction).

## Decisions

- **Why FORCE RLS**: Without `FORCE`, the table owner bypasses policies —
  the single biggest RLS footgun documented by PostgreSQL. The owner
  is the runtime principal in production (Flyway runs as owner + service
  connects as owner then `SET LOCAL ROLE`), so FORCE is mandatory.
- **Why `current_setting('app.tenant_id', true)` with the second
  argument**: Returns NULL instead of throwing when the GUC is unset.
  This is the defense-in-depth branch — the policy then matches zero
  rows, blocking accidental cross-tenant reads even when the application
  forgets to set the session variable. This is tested in
  `unsetTenantIdReturnsZeroRows`.
- **Why opaque TEXT PKs (not UUID)**: `design.md` §5.1 mandates
  "khóa chính opaque, timestamps và version". UUID v4 is a special
  case of opaque; we use format-pinned strings (regex
  `^[A-Za-z0-9_-]{8,64}$`) so they match the OpenAPI / Protobuf
  identifier shape and stay human-debuggable in logs. UUID generation
  is at the application layer (E3.2b) so the migration stays
  format-agnostic.
- **Why `slug` UNIQUE global, not per-tenant**: A slug is a global
  human-readable identifier for the tenant. Cross-tenant slug reuse
  would cause collision in shared URLs (e.g. public sharing links per
  R6). Global uniqueness is enforced at the database level.
- **Why `person_id` nullable**: E3.2 only binds `User` (Keycloak subject)
  to `Membership`. The link from `Membership` → `Person` (the
  genealogical subject) is gated by E4.x verification workflow per R3.
  Schema reserves the column so E4 does not need an `ALTER TABLE … ADD
  NOT NULL` (expand-contract preserved).
- **Why outbox table here but writer in E3.2c**: Schema-level expand —
  E3.2c wires the writer without touching the schema. The outbox
  payload is `BYTEA` (Avro per ADR-E0.5-08) so the relay (E4.7) is
  the only consumer that needs the Apicurio schema id.
- **Why `NOLOGIN` runtime role**: The runtime role must be unreachable
  by a direct database login. The production connection pool user is
  a separate, low-privileged login principal that holds membership in
  `tenant_service_app` and issues `SET LOCAL ROLE` per transaction
  (mirrored by `RlsNegativeIT#newRuntimeSession`).
- **Assumptions**:
  - ADR-E0.5-02 owner-role provisioning is out-of-band (runbook at
    E2.1/E14). The migration grants `tenant_service_app`; the owner
    role must be created by the operator before Flyway runs in
    production (handled by the deployment chart).
  - `app.tenant_id` is set by `TrustedContextFilter` (E1.4 template)
    before any repository call. E3.2a does not wire that filter into
    the IT — the IT sets it manually to prove the policy.
  - Plan/Quota numeric defaults are deferred to E3.2e per the user's
    DRAFT defaults answer (no `CHECK` on quota upper bounds in V2; only
    `>= 0`).

## Residual risks

- **Docker absent locally** — `RlsNegativeIT` cannot run in this sandbox.
  CI must re-run the IT. Mitigation: the migration and IT code are
  byte-identical to the pattern already used by `TenantServiceApplicationIT`
  (Testcontainers `postgres:16.4-alpine` per ADR-E0.5-01 pin); the
  chance of an environmental failure unrelated to the migration is low.
- **`app.tenant_id` must be set per request** — Production code MUST
  set the GUC on every transaction (E3.2c adds a JDBC interceptor that
  reads `TrustedTenantContext.current().getTenantId()` and issues
  `SET LOCAL app.tenant_id = ?`). Until then the policy blocks all
  reads (defense-in-depth) so the production failure mode is "service
  unavailable", not "tenant escape".
- **Outbox table unused** — `outbox_events` is schema-only in E3.2a.
  The writer lands in E3.2c; relay in E4.7. Until then rows are never
  inserted and the table stays empty.
- **`tenants.slug` global UNIQUE** — May surprise operators who assume
  per-tenant slugs (not the case — slug is the public identifier).
  Documented in the table CHECK + column COMMENT in V2.
