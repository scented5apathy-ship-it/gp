Design highlights:

- **Type-tag equality**: `OpaqueId.equals` returns false across
  subclasses so `TenantId("x")` never equals `UserId("x")` even though
  the underlying string matches. Test
  `typeTagPreventsCrossDomainEquality` proves this.
- **Framework-free**: zero Spring, JPA, jOOQ, Flyway imports. The
  domain compiles standalone in 1s (verified by `./gradlew
  compileJava` on just this module).
- **Aggregate invariants match V2 CHECK constraints**:
  - `Tenant.rehydrate` rejects `status=SUSPENDED` with
    `suspendedAt == null` and vice-versa.
  - `Membership.rehydrate` rejects `INVITED` without `invitedAt`,
    `ACTIVE` without `joinedAt`, `SUSPENDED` without both `joinedAt`
    and `suspendedAt`, `REVOKED` without `revokedAt`.
  - `Invitation.rehydrate` rejects simultaneous `acceptedAt` +
    `revokedAt`.
- **Plan/Quota numerics are DRAFT**: `Entitlement` accepts `0`
  (= unlimited) for every quota field and the `canAddMember` check
  short-circuits on `limit == 0`. The service does NOT block
  mutations based on quota; the DRAFT note lives in the class
  Javadoc and in `evidence/E3.2e.md` (deferred per the user's
  answer on Plan/Quota defaults).
- **Membership ↔ Person separation**: `Membership` holds a nullable
  `personId` field — the link is intentionally null in E3.2b because
  the verification workflow lives in E4.x (per `tasks.md` E4.2 "Không
  liên kết User↔Person nếu chưa qua verification workflow").

## Decisions

- **Why 4 shared enums inside `contracts/events/tenant/v1/`**: each
  event references one or more of these enums (plan, status, role).
  Defining them inline per-event makes BACKWARD evolution painful —
  adding a `TRIAL` plan value would require editing 5 schemas
  instead of 1. Keeping the enums in the same `tenant.v1` namespace
  preserves the contract-monolith design (per ADR-E0.5-08 BACKWARD
  policy); the alternative — putting them in `events/shared/v1/` —
  would leak tenant concepts into the shared layer.
- **Why `TenantDisplayName` instead of `DisplayName`**: JUnit 5's
  `@DisplayName` annotation collides with the value-object name when
  test classes import both. Renaming the VO (rather than the
  annotation) preserves the semantic name in the domain and matches
  the eventual goal of having `AccountDisplayName`,
  `MembershipDisplayName`, etc. for other aggregates.
- **Why `Membership.personId` nullable**: per `tasks.md` E4.2 the
  User↔Person link requires an E4.x verification workflow; E3.2b
  reserves the column so E4 does not need an `ALTER TABLE … ADD
  NOT NULL` (expand-contract preserved across schema versions).
- **Why `Invitation.DEFAULT_TTL = 7 days`**: R1 acceptance criterion
  2 mentions "email/link có hạn dùng" without a numeric value; 7
  days is the typical SaaS invite TTL (Stripe, Notion, Linear) and
  is exposed as a config flag in E3.2c (`platform.tenant.invitation.ttl-days`)
  so operators can shorten it for high-risk tenants.
- **Why `TokenHash` accepts up to 128 chars**: hex-encoded
  HMAC-SHA-256 = 64 chars; 128 leaves slack for future SHA-3 /
  Argon2 hashes without a schema migration. The raw token is never
  persisted; only the salted hash from Vault (E3.2c) is stored.
- **Why zero-quota = unlimited**: per `architecture-decisions.md`
  §A the numeric values are DRAFT; `0` is the safe sentinel for
  "unlimited" so a developer can seed the entitlement with `0`
  before the E0.6 sign-off sets the real caps. The service emits
  a warning via `canAddMember` (advisory only — the application
  service does not block mutations on quota in E3.2b).
- **Why exhaustive switch + default branch in `TenantStatus` and
  `MembershipStatus`**: Checkstyle enforces a `default` clause on
  every `switch` statement. Adding `default -> false` (or
  `default -> throw` for rehydrate) gives the static checker
  something to anchor on AND documents the future-proof behaviour
  for unknown enum symbols.
- **Why framework-free domain**: `agent-execution.md` §4.4 + R3
  boundary discipline. The repository layer (E3.2c) adapts V2
  columns to these types; the application service depends on the
  domain; the REST/gRPC adapters depend on the application service.
  No circular deps, no framework leak.
- **Assumptions**:
  - `OpaqueId.FORMAT` matches every layer (database CHECK, OpenAPI
    pattern, Avro `OpaqueId`). Drift is detected by the existing
    `ContractInvariantsTest` (already passes).
  - The runtime `IdGenerator` (UUIDv4 hex with dashes) lands in
    E3.2c with Spring `@Configuration`. The `IdGenerator`
    interface lives here so the unit tests can inject a
    deterministic implementation.
  - Plan/Quota numeric defaults will be ratified by E0.6; the
    DRAFT values stay documented in `evidence/E3.2e.md` (out of
    scope for E3.2b but flagged so the operator does not confuse
    `0 = unlimited` with a missing setting).

  `tenantId`/`tenantScope` fields and never accept a cross-tenant
  reference. The `Tenant` aggregate enforces `tenant_id = id` (self-
  scope root) — the database V2 CHECK mirrors this.
- **Authorization / ABAC**: N/A — the ABAC layer lands in E3.4.
  E3.2b is the data model + event shape.
- **Secret / PII / DNA leakage**: PASS.
  - `Email` is documented as PII (audit hook MUST redact before

  - `TokenHash` is the only token-derived field persisted; the raw

  - No DNA fields anywhere (lint-events + test-contracts both

  - `UserId` is the Keycloak `sub` pseudonym per ADR-E0.5-05; the

- **Dependency / config scan**: N/A in this change set (no new
  dependencies; only existing `libs.platform-spring-boot-starter`

## Residual risks

- **Plan/Quota numerics are DRAFT**: `Entitlement` accepts `0` for
  every quota and treats it as "unlimited". The real caps come from
  E0.6 sign-off; until then the service emits advisory warnings
  via `canAddMember` but does NOT block mutations. E11.4 owns the
  real quota enforcement. Documented in `evidence/E3.2e.md`
  (out of scope for E3.2b).
- **`Membership.personId` reserved column without writer**: the
  schema has the column but the domain aggregate does not expose a
  setter — the verification flow that links User↔Person lands in
  E4.x. Until then the column stays null. expand-contract safe
  (NULLABLE column + no domain mutation).
- **Invariants duplicated between V2 migration CHECK and Java
  domain**: any drift is detected by the `RlsNegativeIT` suite
  (E3.2a) AND by `DomainInvariantsTest.rehydrate` reject cases
  (E3.2b). The two layers are kept in sync by hand until a future
  jOOQ generator codegen step (out of scope for E3.2b).
- **Enum evolution**: BACKWARD per ADR-E0.5-08 means we can ADD
  symbols (e.g. `TRIAL` plan) without bumping `v2`; REMOVING a
  symbol requires a new version. The exhaustive switch in
  `canTransitionTo` returns `false` for unknown symbols so a future
  enum addition cannot accidentally open a transition edge.
