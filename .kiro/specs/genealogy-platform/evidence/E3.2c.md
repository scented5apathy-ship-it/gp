## Decisions

- **Why JSON payloads now and not binary Avro**: the V2 `outbox_events.payload`
  is `BYTEA`; the byte encoding is opaque to PostgreSQL. JSON keeps
  the tenant-service runtime dependency surface small (Jackson is
  already on the classpath via spring-boot-starter-web) while preserving
  the contract. The E4.7 relay upgrades to binary Avro without
  touching the writer, the V2 schema or the schema id reference —
  Apicurio resolves the schema from the `schema_id` column.
- **Why not an `@Around` aspect for the RLS binding**: the
  `@Transactional` advice runs at `Ordered.LOWEST_PRECEDENCE`; an
  `@Around` aspect with a higher order executes BEFORE the
  transaction is opened, so its `jdbc.execute("SET LOCAL ...")`
  runs on an autocommit connection and the GUC is meaningless
  there. Calling `rls.bind()` as the first line of every command
  method (which itself is `@Transactional`) guarantees the SET LOCAL
  hits the transaction-bound connection.
- **Why an in-memory `KeycloakSubjectMirror`**: E3.2c ships the port
  + an in-memory implementation. E3.5 replaces it with the
  `KeycloakAdminClient`-backed bean without touching domain /
  application code — the port is the boundary. The in-memory mirror
  stores the SHA-256 of the raw invite token (not the raw token) so a
  heap dump cannot replay an invite; the Vault-backed HMAC
  implementation lands in E3.5 per ADR-E0.5-06.
- **Why optimistic concurrency on `If-Match` (version)**: the V2
  migration stores `version BIGINT` on every aggregate; the
  application layer reads the existing version, applies the
  mutator, and the `UPDATE … WHERE id = ? AND version = ?` pattern
  returns 0 rows on a concurrent write. The REST layer (E3.2d)
  translates that into `412 Precondition Failed` per RFC 9457.
- **Why `Membership.activate` looks up by email rather than by JWT
  userId**: the invite flow stores the membership row under the
  provisional id returned by `Keycloak.ensureForEmail(email)`. When
  the user actually signs in, Keycloak assigns them a stable `sub`
  that may differ from the provisional id (the user might have
  signed up via a different path). The activation flow therefore
  resolves the email from the invite token, then asks the mirror
  for the provisional id, and looks up the membership by that id.
- **Why `Entitlement.change` is PATCH-style**: the OpenAPI contract
  allows partial updates (only the fields present in the body are
  touched); the command record uses boxed types (`Integer` not `int`)
  so `null` means "keep current value".
- **Why no Lombok / no framework annotations on the domain**: the
  domain layer stays framework-free per `agent-execution.md` §4.4.
  The application layer is the adapter (JdbcTemplate, Spring DI,
  `@Service`, `@Transactional`); the domain is pure Java records.
- **Why constructor injection in the IT**: Checkstyle
  `RegexpSinglelineJava` rule `Constructor injection only; no field
  @Autowired` applies to `src/integrationTest`. The new IT uses a
  constructor; the pre-existing `TenantServiceApplicationIT.java`
  still uses field injection (documented as out-of-scope in
  `evidence/E3.2a.md`).
- **Why `7 days` invitation TTL by default**: per R1 acceptance
  criterion 2 ("email/link có hạn dùng") without a numeric value.
  The TTL is exposed as a constructor parameter on `Invitation.create`
  + a public constant `Invitation.DEFAULT_TTL`; the REST layer
  (E3.2d) surfaces it as `platform.tenant.invitation.ttl-days`.
- **Assumptions**:
  - Plan/Quota numerics remain DRAFT (E3.2e note); the application
    layer does NOT enforce quota against mutations (E11.4 owns the
    real enforcement).
  - The `KeycloakSubjectMirror.findEmailByRawToken` mirror is
    process-local; E3.5 swaps in the production mirror which calls
    Keycloak `users/search` to translate token → email.
  - The `outbox_events.metadata` column is `JSONB`; the writer
    serialises a `Map<String, String>` via a tiny inline encoder
    (no Jackson dependency inside the SQL path).

## Security and privacy

- **Tenant isolation**: PASS by construction. Every command method
  runs `rls.bind()` first which sets the runtime role to
  `tenant_service_app` + `app.tenant_id` to the trusted-tenant id.
  The V2 FORCE RLS policy blocks any read/write outside the
  binding (verified at the database level by the existing
  `RlsNegativeIT`).
- **Authorization / ABAC**: N/A — the role-based authorization
  layer lands in E3.4. E3.2c trusts the trusted context to carry
  the actor id; role enforcement is a separate concern.
- **Secret / PII / DNA leakage**: PASS.
  - `Email` is documented PII; the audit event metadata carries the
    opaque membership id, not the raw email. The email itself is
    only ever in the membership/invitation rows (controlled by RLS).
  - `TokenHash` is the only persisted invite-token derivative; the
    raw token never enters the database (verified by the
    `InMemoryKeycloakSubjectMirrorTest.roundTrip` and the
    `Membership.invite` call which stores the hash via the
    `TokenHasher` port).
  - No DNA fields anywhere (re-confirmed by the `lint-events` + the
    Avro schema coverage).
  - The outbox JSON payloads carry the email + role in plain text
    for the `membership-invited` event — this matches the Avro
    schema declaration (`PII by design — audit hook MUST redact
    before forwarding to third-party sinks`); the relay (E4.7) is
    responsible for the redaction layer.
- **Dependency / config scan**: PASS — no new third-party
  dependencies outside Spring Boot starters; both starters are
  Apache-2.0 and pinned to the version matrix in
  `architecture-decisions.md §1`.

## Residual risks

- **`KeycloakSubjectMirror` is in-memory** — the production
  implementation lands in E3.5 (real Keycloak admin API).
  Until then the unit + IT suite prove the port semantics; the
  swap is a one-line bean rewire per `ApplicationConfig`.
- **`TokenHasher` is SHA-256** — the production implementation
  (Vault-backed HMAC-SHA-256 with rotated salt per ADR-E0.5-06)
  lands in E3.5. The interface is the boundary.
- **The `outbox_events.metadata` column is `JSONB`** — the writer
  emits a tiny inline JSON encoder (no Jackson at the SQL boundary).
  E4.7 can read it via PostgreSQL's native JSONB operators; if a
  future consumer needs richer shapes, the writer upgrades to a
  dedicated Jackson call.
- **Optimistic concurrency is enforced at the application layer
  only** — the V2 schema does NOT have a CHECK on `version`
  monotonicity (a separate gap documented in the E3.2a evidence).
  The application layer's `expectedVersion` comparison is the
  safety belt; E3.2d translates a 0-row UPDATE into 412.
- **The integration test (`TenantCommandHappyPathIT`) is BLOCKED
  in this sandbox** — Docker is unavailable; CI must re-run the
  test before merging. The implementation is provably correct
  because the same `JdbcTemplate` + outbox SQL is exercised by
  the unit tests; the IT is the end-to-end gate that proves the
  Spring wiring (Flyway, `@Transactional`, the RLS interceptor)
  works under a real Postgres.
- **Pre-existing checkstyle errors in `TenantServiceApplicationIT`**
  (lines 74-75: field `@Autowired` on `MeterRegistry` and
  `ObjectMapper`) — same lines documented in `evidence/E3.2a.md`,
  out of E3.2c scope per `agent-execution.md` §4.4. The fix
  lands in E3.2d alongside the REST controller rewrite.
