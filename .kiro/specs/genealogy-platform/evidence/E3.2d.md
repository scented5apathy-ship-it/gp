## Decisions

- **Why a separate `web` package instead of folding into `application`**: the
  application layer is framework-free; web annotations
  (`@RestController`, `@RequestBody`, etc.) stay in `web/`. The
  `application` package still owns the use cases; `web/` adapts
  HTTP → `Commands` records. Mirrors the layered split in
  `services/person-service` and keeps the dependency arrow
  `web → application → domain` one-directional.
- **Why `404` for cross-tenant, not `403`**: a probe that gets
  `403` learns the tenant exists; a probe that gets `404` cannot
  distinguish "tenant does not exist" from "tenant belongs to
  someone else". Per the OpenAPI documentation (`tenant.yaml`)
  the response code is `404` for any tenant that the caller
  cannot see, which is the contract the cross-tenant negative
  test enforces.
- **Why server-side invite token mint**: the OpenAPI
  `InviteMemberRequest` does NOT include a token field. Minting
  it server-side keeps the contract honest (the wire body never
  carries a secret), guarantees 192-bit entropy (SecureRandom, 24
  bytes hex), and lets the email-service (E4.x) read the
  `invitations` row + send the raw token by email without the
  caller having any way to inject a malicious value.
- **Why `If-Match` is required, not optional, for mutations**:
  every write goes through a repository `UPDATE … WHERE id = ?
  AND version = ?` so a missing `If-Match` would surface as
  `OptimisticConcurrencyException` from the SQL layer. Requiring
  it at the controller boundary turns "client forgot the
  precondition" into a clean 412 instead of a 500.
- **Why the in-memory `IdempotencyCache` (not a Redis call)**:
  the V2 migration does not include an idempotency table; the
  audit hook (`TenantAuditPublisher`) is fire-and-forget so a
  Redis call on the hot path would couple tenant-service to the
  Valkey stack landing in E15. The cache is good enough for the
  retry-within-24h use case (the documented OpenAPI window).
  The contract guarantees the same wire bytes on retry so a
  future durable cache can drop in without changing the public
  surface.
- **Why `Cursor` is a base64-encoded `createdAt|id` tuple**: a
  cursor must be opaque to clients and stable across page
  requests. Encoding the `(createdAt, id)` tuple gives us a
  strict-greater-than comparison in the SQL `WHERE` clause; a
  plain offset would break when a tenant is created between
  requests. The tuple format is internal — the client only sees
  the base64 blob.
- **Why the controller calls `rls.bind()` is NOT necessary at the
  REST boundary**: the trusted `TenantRlsTxInterceptor` is invoked
  by the `*CommandService` and `*QueryService` `@Transactional`
  methods, so every read/write path already binds RLS. The REST
  layer only has to enforce path-vs-header ownership equality.

## Security and privacy

- **Tenant isolation**: PASS by construction. Every controller
  route calls `validateOwnership(trusted, pathTenantId)` which
  throws `TenantNotFoundException` (→ 404) when the path
  `tenantId` does not match `TrustedTenantContext.current().getTenantId()`.
  The same `rls.bind()` from E3.2c runs in the command + query
  services so the SQL `FORCE ROW LEVEL SECURITY` policy matches
  the same tenant id the controller trusted. The cross-tenant
  negative test (`crossTenantAccessReturns404`) and the
  cross-tenant membership negative test
  (`crossTenantMembershipInviteReturns404`) prove the path.
- **Authorization / ABAC**: N/A — the role-based authorization
  layer (OpenFGA + ABAC overlays per ADR-E0.5-05) lands in E3.4.
  E3.2d trusts the trusted context to carry the actor id; role
  enforcement is a separate concern. The `X-User-Id` header is
  NOT read — the controller derives `actorId` from the JWT
  subject via `TrustedTenantContext.current().getActorId()` so a
  client cannot impersonate.
- **Secret / PII / DNA leakage**: PASS.
  - `Email` is documented PII; the audit event metadata carries
    the opaque membership id, not the raw email. The
    `Invitation` response does include the email (the OpenAPI
    contract requires it) but the response is tenant-bound
    (RLS) so a caller without the tenant id cannot read it.
  - `TokenHash` is the only persisted invite-token derivative;
    the raw token is generated server-side with
    `SecureRandom.nextBytes(24)` and returned ONCE in the
    `Invitation.rawInviteToken` field. The email-service (E4.x)
    is the only consumer; the wire contract guarantees the
    token never reappears on subsequent calls.
  - No DNA fields anywhere (re-confirmed by `lint-events` +
    `test-contracts`).
- **Dependency / config scan**: PASS — no new third-party
  dependencies; every new class lives inside the existing
  `tenant-service` Maven coordinates so the `gradle.lockfile`
  is unchanged (the `check-gradle-lockfile.mjs` script passes
  without re-running `--write-locks`).

## Residual risks

- **In-memory `IdempotencyCache` is process-local** — a rolling
  restart loses replay history; a duplicate POST within the 24h
  window after a restart could land as a 409 `idempotency-conflict`
  (the V2 unique `(tenant_id, idempotency_key)` index on
  `invitations` is the durable backstop). The dedicated durable
  idempotency backend lands in E15.
- **Cursor pagination is `(createdAt, id)`-tuple based** — a
  millisecond-level clock skew across writers could (in theory)
  surface a row twice across pages. The `id` tiebreaker keeps the
  ordering deterministic; the SQLite-style `ORDER BY created_at
  ASC, id ASC LIMIT ?` pattern is the standard fix and matches
  the pattern used in `services/person-service`.
- **MockMvc unit test uses `standaloneSetup`** — the
  Spring-managed `IdempotencyCache` bean in production is
  auto-discovered, but the test instantiates it via the
  constructor with a fixed `Clock`. The Testcontainers IT uses
  the real Spring context so the wiring is exercised in CI.
- **Server-side raw invite token is exposed on the invite
  response** — per the OpenAPI contract the `Invitation` schema
  includes `rawInviteToken`. The email-service (E4.x) is the
  only downstream consumer and is the only place the token is
  forwarded to the invitee. Future hardening: switch the
  response field to a one-time `acceptUrl` so the raw token
  never leaves the service boundary (deferred to E4.x with the
  notification-service spec).
- **Integration tests (`TenantServiceApplicationIT`) are
  BLOCKED in this sandbox** — Docker is unavailable; CI must
  re-run before merge. The MockMvc unit suite + the
  Testcontainers `TenantCommandHappyPathIT` from E3.2c cover
  every layer below the REST surface; the REST IT is the
  end-to-end gate that proves the Spring Boot context + Flyway +
  RLS + REST controllers wire together correctly.
