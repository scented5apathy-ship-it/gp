## Decisions

- **Why a Spring `@Component` and not a real `BindableService`**:
  the E1.3 contract ships `tenant_service.proto` + a few
  sibling enums (`TenantStatus`, `MembershipStatus`, etc.)
  whose value names collide inside the package
  (`TenantStatus.ACTIVE` vs `MembershipStatus.ACTIVE`,
  `TenantStatus.SUSPENDED` vs `MembershipStatus.SUSPENDED`).
  `protoc` rejects the file until the collisions are
  resolved; the resolution is owned by E4.x along with the
  `com.google.protobuf` Gradle plugin wiring. Per the E3.2e
  DoD the gRPC surface MUST be a stub only; the REST surface
  is the contract of record.
- **Why `git mv` the placeholder rather than leave it as-is**:
  the E3.2e DoD names the class `TenantGrpcService`; the
  Checkstyle `ClassDataAbstractionCoupling` +
  `AbbreviationAsWordInName` rules forbid underscores in
  class names (the existing `Placeholder` suffix is no longer
  accurate since the E1.4 reasoning — "the implementation
  lands in E3.2" — has been refined by the E3.2 split into
  a/b/c/d/e).
- **Why the runbook does NOT cite specific replica counts,
  HPA thresholds, PDB minima, or probe paths**: no
  tenant-service Helm workload template has been rendered yet
  (verified by `find platform/helm -name '*tenant*'` →
  empty). Documenting non-existent resources would mislead
  the on-call operator; the runbook explicitly marks them
  as "DEFERRED" and points at the E2.1 component rollout
  owner (`platform-primary`).
- **Why the alert file is NOT shipped in E3.2e**: the task
  spec explicitly defers it to E13.2 (no prometheus-rules
  linter for service-scoped rules exists yet — verified by
  `ls scripts/lint-prometheus-rules.mjs` → missing). The
  runbook documents the alert skeleton as a deferred path;
  shipping the file would be a scope expansion under §4.4.
- **Why the runbook labels every numeric as `DRAFT` and points
  at the E0.6 sign-off ceremony rather than the E0.6 task
  completion**: the E0.6 task evidence marks the sign-off
  ceremony itself as outstanding (the E0.6 task is DONE but
  the ceremony is recorded in a separate `E0.6-signoff.md`
  file that does not yet exist). Treating "E0.6 task DONE"
  as "numeric thresholds approved" would mis-state the
  governance state.
- **Why the runbook points at E11.4 (not E13.4) for quota
  enforcement**: E13.4 is resilience / chaos testing per
  `tasks.md`; quota enforcement, usage metering, warnings,
  and billing adapters are E11.4.
- **Why the runbook references `genealogy.audit.v1.v1` as the
  canonical audit topic**: the canonical Kafka source of truth
  is `platform/kafka/topics.yaml` (audit class, 365-day
  retention, owner `audit-service`). Tenant-service does NOT
  publish directly to it in E3.2 — its outbox is
  relay-mediated and the relay lands in E4.7. Naming a fake
  `gp.tenant.v1.audit` topic in the runbook would conflict
  with the E2.3 ADR-E0.5-08 naming rule
  (`<domain>.<aggregate>.<version>.v<n>`).
