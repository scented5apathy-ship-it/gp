### New — `libs/platform-spring-boot-starter/src/main/java/.../grpc/` (E3.5 wire contract executor)

- `TrustedContextMetadataKeys` — closed-set metadata key
  constants (`x-tenant-id`, `x-actor-id`, `x-actor-role`,
  `x-correlation-id`, `x-idempotency-key`, `x-user-agent`,
  `x-peer-spiffe-id`).
- `TrustedContextReconstructor` — framework-free POJO. The
  `InboundCall` record is the snapshot every gRPC server
  builds; the reconstructor validates it against the contract
  and returns the server-derived `TrustedTenantContext`.
- `TrustedContextViolation` — closed-set exception with a
  9-entry `Reason` enum (`CLIENT_SUPPLIED_TENANT_ID`,
  `CLIENT_SUPPLIED_ACTOR_ID`, `CLIENT_SUPPLIED_ACTOR_ROLE`,
  `MISSING_SPIFFE_PEER`, `UNTRUSTED_SPIFFE_PEER`,
  `MISSING_TENANT_ID`, `MISSING_ACTOR_ID`,
  `MISSING_ACTOR_ROLE`, `MISSING_CORRELATION_ID`). The
  catalogue is the audit contract.
- `TrustedContextFieldGuard` — defensive validator that
  services call AFTER deserialising the proto `Context` field
  but BEFORE acting on the request. Accepts a
  `ContextView` interface so the guard itself stays
  framework-free.
- `GrpcTrustedContextInterceptor` — gRPC `ServerInterceptor`
  shell. Reads `x-tenant-id` / `x-actor-id` / `x-actor-role` /
  `x-correlation-id` / `x-peer-spiffe-id` metadata, delegates
  to the reconstructor, populates the thread-local
  `TrustedTenantContext` for the duration of the call.
  Surfaces the violation reason in the
  `x-trusted-context-violation` trailer.
- `GrpcTrustedContextClientInterceptor` — gRPC
  `ClientInterceptor` used by the BFF to forward the REST-
  authenticated trusted context as gRPC metadata.

## Security and privacy

- Tenant isolation: PASS — the BFF reconciler rejects tenant
  selections that don't match an `ACTIVE` membership; the
  gRPC interceptor rejects every request whose SPIFFE peer
  isn't in the `gp-bff/sa/...` trust zone or whose
  BFF-issued metadata is missing.
- Authorization/ABAC: PASS — the new code is
  OpenFGA-agnostic; it never decides relationships. The
  reconciler only confirms that a membership exists + is
  ACTIVE; OpenFGA + the ABAC overlay (E3.3 / E3.4) handle
  the authorization decision.
- Secret/PII/DNA leakage: PASS — the linter scans for
  `password=`, `token=eyJ`, `dsn=jdbc:` literals and exits
  non-zero on detection. The reconciler never logs the
  membership payload; only the resolution status is logged
  at INFO level with the opaque tenant + correlation ids.
- Dependency/config scan: PASS — `apps/web-bff` only adds
  Spring Boot starters (Apache-2.0) + the cross-cutting libs.
  No new Docker image. No AGPL. The lockfile is committed.
- Cross-service boundary: PASS — the BFF reconciler depends
  on the tenant-service REST contract (no service-internal
  types); the gRPC interceptor lives in
  `platform-spring-boot-starter` (cross-cutting library,
  allowed by AGENTS.md §2.7).
- mTLS / SPIFFE posture: PASS — the default
  `expectedPeerPattern` constrains the SPIFFE peer to
  `gp-bff/sa/...`; services can override via the
  constructor. Production Istio mTLS is STRICT (E2.5); the
  `inferLocalPeerSpiffe` sentinel is dev-only.
- Audit hook: PASS — every `TrustedContextViolation` is
  logged with the reason code, SPIFFE peer, tenant id,
  actor id, and method name. The interceptor closes the
  gRPC call with `PERMISSION_DENIED` +
  `x-trusted-context-violation` trailer; the audit hook
  picks it up from the SLF4J MDC + Micrometer.

## Acceptance criteria

- [x] **BFF đối chiếu tenant selection với membership** —
  `MembershipReconciler` + `TenantSelectionGuard` in
  `apps/web-bff`; only `ACTIVE` memberships authorise the
  selection; mismatch returns 404 (never 403).
- [x] **Truyền context qua gRPC trong Istio mTLS** —
  `GrpcTrustedContextClientInterceptor` (BFF → service) +
  `GrpcTrustedContextInterceptor` (server side) +
  `x-peer-spiffe-id` metadata key validated against the
  `gp-bff/sa/...` SPIFFE pattern.
- [x] **Service tự xác minh identity/context và luôn thêm
  tenant predicate** — `GrpcTrustedContextInterceptor`
  populates the thread-local `TrustedTenantContext`; the
  existing `TenantRlsTxInterceptor` (E3.2a) reads it and
  binds `app.tenant_id` per-transaction; PostgreSQL RLS
  enforces the predicate. The
  `TrustedContextFieldGuard` rejects client-supplied proto
  `Context` fields at the message body.
- [x] **Từ chối `tenant_id`, role hoặc subject do client
  tự khai báo** — `TrustedContextFilter` rejects query-
  string `tenantId` / `tenant_id` / `role` /
  `actor_role` / `subject` / `actor_id` at the REST edge;
  `GrpcTrustedContextInterceptor` rejects proto `Context`
  fields on the gRPC edge; the linter refuses any drift
  in the closed-set contract.

## Residual risks

- The BFF reconciler calls `tenant-service::ListMemberships`
  on every authenticated request. If the call is slow /
  unavailable, the BFF refuses the request (deny-closed).
  A future epic may add a BFF-side membership cache
  (Redis / Valkey) with short TTL + invalidation on
  membership status flips — outside E3.5 scope.
- The default SPIFFE pattern constrains the BFF peer to
  `gp-bff/sa/...`. Cross-namespace callers (e.g. a worker
  in `gp-workers` calling a service directly) must register
  a custom `TrustedContextReconstructor` bean with a
  broader pattern. E3.5 documents the override; the
  documentation lives in
  `libs/platform-spring-boot-starter/.../grpc/README.md`
  and `runbook/trusted-context.md`.
- The `x-peer-spiffe-id` metadata key is filled by Istio
  only when STRICT mTLS is on. Services running locally
  (dev profile, integration tests) fall back to a
  `dev-local` sentinel — the default pattern allows it.
  Production never sees this branch (E2.5 confirms STRICT).
