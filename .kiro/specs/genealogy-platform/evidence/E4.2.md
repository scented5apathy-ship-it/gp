## Decisions

- **Service keeps the name `genealogy-service`** per
  `ownership-catalog.md` §2.2 — E4.2 only adds the person
  package; renaming would require an ADR supersession.
- **User↔Person link is verification-gated.** `verifiedUserId`
  is `null` on creation and may only be set through
  `linkVerifiedUser(...)` which requires an opaque id handed by
  the verification workflow (out of scope for E4.2). This mirrors
  `requirements.md` R2.4 / R4.6: deleting a User MUST NOT delete
  the Person.
- **All enums are closed-sets** mirroring the YAML contract
  byte-for-byte. The `fromWire` helpers accept the canonical
  `UPPER_SNAKE_CASE` form only; the lint test guarantees the
  Java enum and the YAML stay aligned.
- **Privacy + living-status transitions emit dedicated events**
  so the search / public projections can re-evaluate redaction
  (`design.md` §6.3 obligations). Every mutation emits at least
  one event and is recorded on the append-only `person_history`
  table for audit + reversal (E4.6 merge history).
- **Optimistic concurrency via `version`.** Every command
  increments `version` by exactly 1 and the repository rejects
  stale versions. The diff helper emits a closed-set list of
  changed field paths; the event payload carries the previous +
  new version so consumers can detect dropped updates.
- **Append-only `person_history`** is enforced by a Postgres
  trigger that rejects UPDATE / DELETE and by a `GRANT` that
  forbids UPDATE on the table from the application role.
- **No raw DNA / biography / identifier value / access token
  is ever placed in event payloads** per `design.md` §7.3 —
  verified by the linter's forbidden-token scan plus the
  `PersonEventPayloads` shape: biographies are summarised by
  `nameCount` only; identifier `value` is dropped.
- **Living-person predicate** is encoded in
  `LivingStatus#isLiving()` so the renderer / projection layer
  can route on it deterministically (both `LIVING` and
  `INFERRED_LIVING` force PUBLIC / UNLISTED redaction).

## Security and privacy

- Tenant isolation: PASS — `person_tenant_isolation`,
  `person_name_tenant_isolation`,
  `person_pronoun_tenant_isolation`,
  `person_identifier_tenant_isolation`,
  `person_history_tenant_isolation` RLS policies on every
  tenant-scoped table; `FORCE ROW LEVEL SECURITY`; the
  application role `tree_service_app` is scoped to the
  `tree_service` schema only per ADR-E0.5-02.
- Authorization/ABAC: PASS — `linkVerifiedUser(...)` is the
  only path that touches `verifiedUserId`; the field is
  non-nullable only after a verification workflow hands an
  opaque Keycloak sub. Person mutation requires the actor to
  be authorised at the gRPC trusted-context layer (E3.5).
- Secret/PII/DNA leakage: PASS — biography, identifier
  `value`, raw DNA and access tokens never appear in any
  event payload (enforced by `PersonEventPayloads` shape +
  linter forbidden-token scan). The `person_history` JSONB
  snapshot MAY carry the profile but MUST NOT carry raw DNA
  / file content / access tokens (snapshot is built from the
  aggregate, which already excludes those).
- Append-only audit: PASS — `person_history` is enforced
  append-only by a Postgres trigger that raises on UPDATE /
  DELETE; the application role only has `SELECT, INSERT`.
  Privacy / living-status / soft-delete transitions emit
  dedicated events with audit-class=consent (matches
  `contracts/audit/policy.yaml`).
- Dependency/config scan: PASS — no literal secret / token /
  password / DSN in any source-of-truth file (linter +
  chart-mirror byte-equality enforced).

## Acceptance criteria (tasks.md line 333-337)

- [x] Multi-name / script / alias / pronoun / living status /
  biography / identifiers / field privacy. The `Person`
  record carries `names[]`, `pronouns[]`, `identifiers[]`,
  `livingStatus`, `privacyLevel`, `genderDescription`,
  `biography`. `PersonName` carries `kind / scriptTag /
  localeTag / display / romanised / preferred`. `PersonIdentifier`
  carries `kind / value / sourceSystem / verified`. The closed
  enums mirror `contracts/genealogy/person-policy.yaml`.
- [x] Optimistic version / ETag. The `version` field is
  monotonic; the repository enforces CAS (`WHERE
  version = previous`); every command increments by exactly 1;
  the `PersonUpdatedEvent` carries `aggregateVersion` and
  `previousVersion` so consumers detect dropped updates.
- [x] Records actor, reason, diff. Every command record
  carries `actorId` + `reason`. `Person.diff(before, after)`
  returns a closed-set list of dotted field paths; the
  `PersonUpdatedEvent.changedFields` array carries it.
- [x] No implicit User↔Person linking. `verifiedUserId` is
  `null` on creation and only `linkVerifiedUser(...)` sets it
  with an opaque id. `person-policy.yaml` declares
  `userLinkRequiresVerification: true`; the linter enforces
  it.
