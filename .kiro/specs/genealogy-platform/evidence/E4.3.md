## Decisions

- **Service keeps the name `genealogy-service`** per
  `ownership-catalog.md` §2.2 — E4.3 only adds date / calendar /
  place types to the existing aggregate module.
- **Provider-neutral authority reference.** The contract pins
  `AuthorityKind` (WIKIDATA / GEONAMES / NATIONAL_GAZETTEER /
  LOCAL) but keeps the authority id opaque. Swapping providers
  is a config-only change per `requirements.md` R4.4.
- **Closed-set qualifier.** `EXACT / ABOUT / BEFORE / AFTER /
  BETWEEN / UNKNOWN` mirrors `design.md` §5.3; the Java executor
  enforces the qualifier-vs-interval shape so a BEFORE row
  cannot carry a BETWEEN interval. UNKNOWN is explicit so the
  renderer never silently picks EXACT.
- **Closed-set calendar.** `GREGORIAN / JAPANESE /
  VIETNAMESE_LUNISOLAR / KOREAN / CHINESE_LUNISOLAR /
  ISLAMIC_CIVIL / HEBREW / FRENCH_REPUBLICAN` mirrors
  `tree-policy.yaml::spec.supportedCalendars` plus the
  Vietnamese + Korean lunisolar calendars that the E4.3
  recurring-memorial flow needs.
- **UTC is the only canonical instant.** `storageTimezone: UTC`
  in the contract; the IANA timezone is preserved alongside
  the original expression so the renderer can reformat the
  date in any timezone without losing information.
- **Place hierarchy depth is capped at 8.** Deeper chains are
  rejected at the application layer so the renderer / search
  projection can rely on bounded fan-out.
- **No new event schemas in this subtask.** Date / place
  change events will land with the consuming aggregates (E4.4
  relationship, E4.5 event). The audit hooks
  (`auditClassOnDateChange`, `auditActionOnDateChange`, …)
  declared in the YAML give the change-event schemas a stable
  contract to align against.
- **Living-person redaction is on by default.**
  `livingPersonRedactsByDefault: true` matches R10 + the
  existing `Person.livingStatus` redaction surface.
- **Recurring memorial enabled.** `recurringMemorialEnabled:
  true` per R10; the renderer chooses between Gregorian and
  per-calendar recurrence based on `CalendarId.isLunisolar()`.

## Security and privacy

- Tenant isolation: PASS — `date_value_tenant_isolation` +
  `place_tenant_isolation` RLS policies on every tenant-scoped
  table; `FORCE ROW LEVEL SECURITY`; the application role
  `tree_service_app` is scoped to the `tree_service` schema
  only per ADR-E0.5-02.
- Authorization/ABAC: PASS — date / place rows carry
  `tenantId` + (for Place) `createdBy`. Authority links are
  provider-neutral and never embed API keys (the
  `authorityId` regex enforces an opaque id shape).
- Secret/PII/DNA leakage: PASS — no literal secret / token /
  password / DSN in any source-of-truth file (linter +
  chart-mirror byte-equality enforced). Date / place change
  events will reuse the existing
  `person-updated.avsc` / `tree-updated.avsc` shape and MUST
  NOT carry raw DNA / biography / identifier values (the
  follow-up event schema in E4.4 / E4.5 will keep the
  forbidden-token scan).
- Coordinate privacy: PASS — coordinates are capped at
  `DECIMAL(9,6)` (≈ 0.11 m). Living-person place rows are
  NOT auto-redacted (place is shared infrastructure), but the
  `Person` aggregate carries the `livingStatus` redaction
  surface so any `DateValue` on a living person is rendered
  with the existing living-person redaction.
- Dependency/config scan: PASS — `place_authority_idx` is
  scoped to the tenant; no cross-tenant authority resolution.

## Acceptance criteria (tasks.md line 339-343)

- [x] Hỗ trợ exact/about/range/before/after/unknown và giữ
      original expression. `DateQualifier` exposes the closed
      set; `DateValue.originalExpression` preserves the
      verbatim input (≤ 512 chars); `design.md` §5.3 "ABOUT /
      BEFORE / AFTER / BETWEEN" is mapped 1-1.
- [x] Lưu UTC, IANA timezone, calendar ID và normalized
      interval. `DateValue` stores `originalExpression`,
      `calendar`, `qualifier`, `timezone` (IANA-shaped
      regex), and `NormalizedInterval` carries `earliest` /
      `latest` UTC bounds for sort / range queries.
- [x] Place có hierarchy, historical names, coordinates và
      provider-neutral authority reference. `Place` aggregate
      exposes `hierarchy` (≤ 8 depth, no self-reference),
      `names[]` (≤ 32, language-tagged, no duplicate
      `(languageTag, display)`), `coordinates` (WGS84,
      ±90 / ±180), and `authority` (provider-neutral
      `(AuthorityKind, authorityId)` shape).

## Residual risks / follow-up tasks

- **JDBC repository implementation** for `DateValue` /
  `Place` (skipped here to keep the diff scoped to E4.3; the
  in-memory unit-test surface is the executable proof, mirroring
  the E4.1 / E4.2 pattern). The Flyway migration
  (`V4__date_place.sql`) is the persistence contract; the
  JDBC wiring lands in E4.7 alongside the relay.
- **Event schemas** for date / place change (`date.updated`,
  `place.updated`, `place.attached`) land with the consuming
  aggregates (E4.4 relationship, E4.5 event). The audit
  classes / actions declared in the YAML
  (`auditClassOnDateChange = consent` etc.) give the event
  schemas a stable contract to align against.
- **Geocoding provider integration** (Wikidata / GeoNames /
  national gazetteer) is a separate follow-up; the contract
  is provider-neutral on purpose so this is config-only.
- **Recurring memorial renderer** for non-Gregorian calendars
  is the renderer's responsibility; the contract pins
  `recurringMemorialEnabled: true` and
  `CalendarId.isLunisolar()` so the renderer can route
  deterministically.
- **Cross-tenant authority resolution** is forbidden at the
  application layer — the RLS policy + the
  `tenant_id` predicate on `place_authority_idx` both enforce
  this.
