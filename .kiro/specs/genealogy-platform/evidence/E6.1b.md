## Decisions

- **Why FORCE RLS**: Without `FORCE`, the table owner bypasses policies — the single biggest RLS footgun documented by PostgreSQL. The owner is the runtime principal in production (Flyway runs as owner + service connects as owner then `SET LOCAL ROLE`), so FORCE is mandatory.
- **Why `current_setting('app.tenant_id', true)` with the second argument**: Returns NULL instead of throwing when the GUC is unset. This is the defense-in-depth branch — the policy then matches zero rows, blocking accidental cross-tenant reads even when the application forgets to set the session variable. This is tested in `unsetTenantIdReturnsZeroRows`.
- **Why opaque TEXT PKs (not UUID)**: `design.md` §5.1 mandates "khóa chính opaque, timestamps và version". UUID v4 is a special case of opaque; we use format-pinned strings (regex `^[A-Za-z0-9._-]{1,128}$`) so they match the OpenAPI / Protobuf identifier shape and stay human-debuggable in logs. UUID generation is at the application layer (E6.1c / `ApplicationConfig`) so the migration stays format-agnostic.
- **Why CHECK constraints on closed-set enums** (vs PostgreSQL ENUM types): PostgreSQL ENUM types cannot be modified without a full table rewrite, which would conflict with the BACKWARD evolution rule of ADR-E0.5-08. CHECK constraints let us add a new value with a single migration; the existing `scripts/lint-research-config.mjs` validator already alphabetises the Java enum constants so the SQL CHECK and the Java enum stay in lockstep without a schema-per-enum break.
- **Why no cross-schema FK between `sources` and `repositories`**: PostgreSQL CHECK constraints cannot use a subquery, so the tenant ↔ repository consistency cannot be enforced as a SQL CHECK (the broken first-pass attempt is recorded in the commit history). The `Source` Java compact constructor enforces the invariant at the application layer; the SQL CHECK on `repository_id` format pins the column shape.
- **Why inline JSONB arrays on `citations` / `research_tasks` / `conflicts`** (transcript segments, attachments, external urls, linked citation ids): The `tasks.md` §E6.1b scope explicitly lists **exactly five bridges**:
  1. `research_task_assignments`
  2. `hypothesis_corroborating_citations`
  3. `hypothesis_refuting_citations`
  4. `conflict_participants`
  5. `conflict_participant_supporting_citations`

  Inline lists on the parent row are a denormalisation, not a new bridge — the V2 surface stays at exactly 11 tables. When a later sub-task (E6.1d + E11 reports) needs indexed access over those segments, the bridge tables land in a V3 migration with the same RLS contract.
- **Why `linked_at` + composite PK on hypothesis / conflict bridges**: The composite `(hypothesis_id, citation_id)` and `(conflict_id, ordinal, citation_id)` keys match the E6.1a domain record shape so the `Hypothesis.withCorroboratingCitation()` / `withRefutingCitation()` / `Conflict.Participant.supportingCitations` semantics map 1-1. The `linked_at` column is the natural sort key for the audit trail.
- **Why the conflict participant CHECK caps `ordinal` at 16**: Mirrors `research-policy.yaml::spec.maxConflictParticipants: 16`. The application-layer invariant `CONFLICT_REQUIRE_MULTIPLE_PARTICIPANTS` (DENY, in `ResearchInvariants`) is the canonical source for the "≥ 2 participants" rule; the SQL CHECK bounds the per-conflict upper limit so a JDBC rehydration never writes more than the domain allows.
- **Why `create_or_replace_function` for the helper**: The migration runs after V1 (which doesn't touch the function) so `CREATE OR REPLACE FUNCTION` keeps the idempotent partial-run behaviour. If a developer re-runs the migration locally after a failed partial apply, the function is refreshed without an error.
- **Assumptions**:
  - ADR-E0.5-02 owner-role provisioning is out-of-band (runbook at E2.1/E14). The migration grants `research_service_app`; the owner role must exist by the time Flyway runs in production (handled by the deployment chart).
  - `app.tenant_id` is set by `TrustedContextFilter` (E1.4 template) before any repository call. E6.1b does not wire that filter into the IT — the IT sets it manually to prove the policy. The `ResearchRlsTxInterceptor` bean lands in E6.1c alongside the application services.
  - Plan / Quota numeric defaults are out of scope for E6.1b (research-service does not enforce quotas at the data layer; quotas live in `tenant-service::entitlements` per ADR-E0.5-02).
  - The 5 explicit bridges listed in `tasks.md` §E6.1b are the complete set for V2. The 4 additional bridges the domain model suggests (`citation_transcript_segments`, `citation_attachments`, `research_task_linked_citations`, `conflict_linked_citations`) are deliberately deferred to V3 to honour §4.4 (no scope expansion) and §6.3 (no scope reduction).

## Residual risks

- **Docker / Testcontainers absent locally** — `RlsNegativeIT` cannot run in this sandbox (Docker Desktop API returns `400 BadRequestException` to testcontainers on macOS sandbox). CI must re-run the IT. Mitigation: the migration + IT code are byte-identical to the pattern already used by `TenantServiceApplicationIT` and `RlsNegativeIT` (Testcontainers `postgres:16.4-alpine` per ADR-E0.5-01 pin); the chance of an environmental failure unrelated to the migration is low. The manual Flyway apply + RLS smoke against a real Postgres container proved the migration is correct.
- **`app.tenant_id` must be set per request** — Production code MUST set the GUC on every transaction (E6.1c adds a JDBC interceptor that reads `TrustedTenantContext.current().getTenantId()` and issues `SET LOCAL app.tenant_id = ?`). Until then the policy blocks all reads (defense-in-depth) so the production failure mode is "service unavailable", not "tenant escape".
- **Inline JSONB arrays** — `transcript_segments`, `attachments`, `external_urls` on `citations` and `linked_citation_ids` on `research_tasks` / `conflicts` are denormalised JSONB. When a later sub-task needs indexed access (e.g. "find every transcript segment with speaker = X"), the bridge tables land in V3 with the same RLS contract. The V2 surface stays at exactly 11 tables per the explicit `tasks.md` §E6.1b scope.
- **`repositories.tenant_id` is not the tenant-self column** — Unlike `tenant_service.tenants` (where `tenant_id = id`), a research repository belongs to a tenant; cross-tenant repositories are a legitimate read scope. The RLS policy is `tenant_id = current_tenant_id()`, which is the correct semantic.
- **No jOOQ classes generated yet** — The task description calls out "jOOQ repository bind" but the codebase precedent (E3.2a) uses Spring `JdbcTemplate` for the RLS-bound persistence layer (jOOQ codegen is reserved for E4.x cross-service enum collisions). E6.1b wires the Spring JDBC driver + Flyway + Testcontainers so the E6.1c application services can bind the records; the jOOQ-style "tenant-aware query" semantics are enforced by the RLS policy, not by the ORM.
