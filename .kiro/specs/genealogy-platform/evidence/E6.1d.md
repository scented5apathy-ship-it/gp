## Decisions

- `protobuf` plugin wired for the first time in the
  monorepo (per `tenant-service/build.gradle.kts`
  E4.x handoff); the pre-existing
  `tree_service.proto` / `tenant_service.proto` /
  `person_service.proto` / `search_service.proto`
  enum collisions are explicitly excluded by E6.1d
  and remain in the E4.x backlog.
- `import "com/genealogy/platform/..."` paths in the
  pre-existing `genealogy/`, `tenant/`, `search/`
  contracts were stripped to the `common/`, `tenant/`
  relative paths so the include-dir-based resolution
  works. The `search_service.proto` / `tree_service.proto`
  / `person_service.proto` / `tenant_service.proto`
  files are touched in this commit BUT they remain
  unused at runtime (they are excluded from the
  research-service proto source set). The corresponding
  `java_package` (`com.genealogy.platform.<area>.v1`)
  is unchanged so the canonical generated Java
  packages stay intact for E4.x.
- All three research event types publish to the
  canonical `genealogy.research.v1.v1` topic (per
  `platform/kafka/topics.yaml`); the `eventType`
  field in the JSON payload (per the envelope
  contract) carries the discriminator.
- The OpenFGA supplier is currently the
  project-wide noop stub documented in
  `ResearchAbacConfig`; the production roll-out
  needs the real OpenFGA SDK adapter (see Gap 1).
- The Kafka consumer is a test-harness entry
  point; the production `@KafkaListener` bean is
  E6.1e (see Gap 4).

## Residual gaps (must be closed before E6.1d can be `DONE`)

1. **OpenFGA SDK adapter** — `ResearchAbacConfig`
   installs a noop `OpenfgaCheckSupplier` that
   always returns a present check id. The
   production deployment needs a real adapter
   that uses `dev.openfga:openfga-sdk` (already in
   `libs.versions.toml`) with the per-tenant
   store strategy from `platform/openfga/store-strategy.yaml`,
   the canonical `contracts/openfga/model.v1.json`
   model (no `citation_submit` / `conflict_partial_merge`
   relation exists today — a model version bump +
   ADR are required), and a bounded `Check` call
   that fails closed on timeout / error.
2. **FlagChip / Flagsmith ABAC overlay** — the
   task wording references "FlagChip" but no
   `FlagChip` implementation exists in the
   repository. The `OpenFeature` provider in
   `application.yml` is `noop`; the platform
   `platform-feature-flags` library is empty.
   The Flagsmith OpenFeature provider
   (`openfeature-flagsmith-provider` in
   `libs.versions.toml`) needs to be wired as the
   next step. The ABAC overlay currently runs via
   the `DefaultAbacPolicyEngine` (the
   privacy/legal/membership gate) but the
   FlagChip-driven A/B-tested policy
   switch is not yet available.
3. **Production JdbcTemplate
   `ResearchOutboxRepository`** — the production
   outbox table has RLS-FORCE and needs a real
   `JdbcTemplate`-backed
   `ResearchOutboxRepository` that runs
   `SELECT ... FOR UPDATE SKIP LOCKED` to claim
   pending rows. E6.1d ships the
   `InMemoryOutboxRepository` (unit-test only) and
   the contract; the JdbcTemplate implementation
   lands in E6.1e alongside the relay driver.
4. **Spring `@KafkaListener` for
   `TreeVisibilityChanged` + `PersonRedacted`** —
   the E6.1d consumer is a harness entry point; the
   production Spring Kafka wiring (listener
   container, consumer group, manual ACK after
   DB commit, retry / DLT, TLS / SASL identity)
   is a follow-up.
5. **Consumer durable inbox / idempotency
   table** — `design.md` §7.3 + ADR-E0.5-08
   require a per-tenant inbox row written in the
   same transaction as the projection mutation
   (so a re-delivery does not fork the projection).
   E6.1d has no `inbox` table; the
   `applyRedactionOverlay` relies on idempotent
   SQL but is NOT strictly idempotent under
   concurrent re-deliveries.
6. **RLS binding in the relay** — the relay
   currently runs as the `research_service_app`
   role with the trusted tenant context from the
   JDBC connection's session GUC, but the
   `ResearchOutboxRelayRunner` (the scheduled
   driver) was intentionally removed in this
   commit because it created duplicate
   `ResearchOutboxPollingTenantRegistry` beans
   and a broken `@Scheduled` wiring. The E6.1e
   driver must call `rls.bind()` per tenant and
   use a real tenant directory (the current
   `ResearchOutboxPollingTenantRegistry` defaults
   to an empty list).
7. **PersonRedacted producer upstream** —
   `services/genealogy-service/.../KafkaTopicResolver.java`
   does not currently publish a `PersonRedacted`
   event; the research consumer is wired for the
   schema but the upstream will need to start
   emitting it (E2.1 platform wiring + E5.x
   privacy gate).
8. **Research gRPC service ACLs** —
   `platform/kafka/users.yaml` ships the
   `research-service-producer` ACL for
   `genealogy.research.v1.v1` but no
   `research-service-consumer` ACL. The
   `genealogy` producer ACLs are unchanged; the
   research service will need read access to
   `genealogy.tree-visibility.v1.v1` and
   `genealogy.person-redacted.v1.v1` for the E6.1e
   consumer roll-out.
9. **gRPC trusted-context field-guard status +
   trailer preservation** — the
   `ResearchGrpcContextGuard.enforce` helper
   currently catches `TrustedContextViolation`
   and rethrows it as a generic `RuntimeException`.
   The platform contract requires the gRPC call
   to be closed with `PERMISSION_DENIED` + the
   `x-trusted-context-violation` trailer. The
   metadata interceptor (the `GrpcTrustedContextInterceptor`
   shipped in `platform-spring-boot-starter`)
   handles the metadata case but the
   `Context` proto field case is a per-service
   concern. A small `ServerInterceptor` (or a
   `BindableService` wrapper) is the right place
   to translate the runtime exception; the
   E6.1d commit only ships the guard helper.
