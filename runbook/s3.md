# Runbook — S3/MinIO + bucket policy (E2.7)

## Source of truth

| File                                                       | Purpose                                                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `platform/storage/s3-config.yaml`                          | MinIO server posture (image pin, region, TLS, CORS, versioning, replication, SSE-KMS)    |
| `platform/storage/bucket-policy.yaml`                      | 4 buckets (`media`, `media-quarantine`, `dna-raw`, `import-export`) with per-bucket lifecycle / KMS / IAM / CORS / object lock / signed URL |
| `platform/storage/compatibility-matrix.yaml`               | S3 API operations that must work identically on AWS S3 + MinIO (the E2.7 compatibility test) |
| `platform/storage/valkey-config.yaml`                      | Valkey server posture (image pin, region, TLS, ACL, persistence, TTL ceilings, required users) |
| `platform/helm/genealogy-platform/files/storage/*.yaml`    | Mirror of the four above (chart `helm template` reads from here)                         |
| `platform/helm/genealogy-platform/templates/components/storage/*` | Helm templates for the MinIO StatefulSet + Services + SA + Secrets + bucket-init Job + ConfigMaps + NetworkPolicy |
| `platform/helm/genealogy-platform/templates/components/cache/*`   | Helm templates for the Valkey StatefulSet + Services + SA + Secrets + ACL ConfigMap + NetworkPolicy |
| `platform/observability/alerts/s3-rules.yaml`              | 11 Prometheus alerts across 5 rule groups                                                |
| `platform/observability/alerts/valkey-rules.yaml`          | 9 Prometheus alerts across 4 rule groups                                                 |

The platform deep linter is `scripts/lint-s3-config.mjs`
(`pnpm lint:s3`). The compatibility check is
`scripts/check-s3-compatibility.mjs`. The structural
baseline check is `scripts/check-platform-baseline.mjs`
(E2.7 invariants).

## Recovery procedures

Each playbook requires `kubectl` + `mc` (MinIO client) on
PATH and a working kubecontext. The umbrella chart's
`storage-bucket-init` Job is the canonical path to apply
the source-of-truth bucket policy; operators never apply
buckets by hand per `design.md` §13.

### 1. Server down — `<runbook:s3#server-down>`

`S3ServerDown` fired (MinIO unreachable for 2m).

1. `kubectl -n gp-data get pods -l app.kubernetes.io/component=storage`
   — confirm the StatefulSet is down.
2. `kubectl -n gp-data describe statefulset minio` — check
   events (image pull errors, OOMKilled, node eviction).
3. `kubectl -n gp-data logs -l app.kubernetes.io/component=storage
   --tail=500` — search for `panic`, `error`, `FATAL`.
4. If the StatefulSet crashed during a chart upgrade,
   rollback: `kubectl -n gp-data rollout undo
   statefulset/minio`.
5. If the underlying `gp-data-ssd` PVC is full, expand it:
   `kubectl -n gp-data edit pvc data-minio-0` (set
   `spec.resources.requests.storage`).
6. Once MinIO is Ready, re-run the bucket-init Job:
   `kubectl -n gp-data create job --from=cronjob/...`
   (or `helm upgrade` chart).

### 2. Head latency high — `<runbook:s3#head-latency>`

`S3HeadLatencyHigh` (100ms p95) /
`S3HeadLatencyCritical` (500ms p95) fired.

1. `kubectl -n gp-data exec -it minio-0 -- bash` and
   `mc admin info` — check the cluster status.
2. Investigate the disk latency:
   `kubectl -n gp-data exec -it minio-0 -- iostat -dx 1 5`.
3. Investigate the KMS provider (Vault / cloud KMS) — a
   slow KMS call drags every object operation. Run
   `vault read sys/seal-status` to validate Vault
   availability.
4. Check the audit log for `S3SignedUrlTtlViolation` —
   a misconfigured signed URL TTL may be replaying
   through the cache.

### 3. API error rate — `<runbook:s3#api-errors>`

`S3ServerErrorRateHigh` (1%) /
`S3ServerErrorRateCritical` (5%) fired.

1. `kubectl -n gp-data logs -l app.kubernetes.io/component=storage
   --tail=1000` — search for the failing API.
2. `mc admin trace` — collect the last 100 API calls
   and identify the failing one.
3. If the failure is `AccessDenied` on a signed URL,
   check the application-side `KmsProvider` (E2.6) for
   the bucket's KMS key alias. A rotated key may have
   invalidated older signed URLs.
4. If the failure is `NoSuchBucket`, the `mc` client
   dropped the bucket — re-run the `storage-bucket-init`
   Job.

### 4. Signed URL TTL violation — `<runbook:s3#signed-url-ttl>`

`S3SignedUrlTtlViolation` fired (signed URL TTL > 1 hour).

1. The application code MUST generate signed URLs with
   TTL ≤ 1 hour (export bucket ≤ 15 min). A violation
   means a deployment slipped through review.
2. `mc admin trace` → look for the offending
   `presign-url` call.
3. Roll back the deployment that introduced the
   violation. The `bucket-policy.yaml` invariants
   reject the TTL > 3600 in CI but a runtime
   enforcement at the application layer is required
   for E2.7 to be considered complete.

### 5. Storage low disk — `<runbook:s3#low-disk>`

`S3StorageLowDisk` (85%) / `S3StorageNoDisk` (95%) fired.

1. Identify the bucket with the highest growth:
   `mc du --depth=2 local/`.
2. For `media-quarantine`: check the scan worker
   (E7.1) — abandoned multipart uploads are a
   canonical cause. Run `mc admin rebalance` +
   `mc admin scanner` to force a scan.
3. For `dna-raw`: the bucket is on legal hold
   (E10.5). Expansion is the only path; do not
   delete objects without a consent revocation.
4. For `import-export`: lifecycle expiry should
   purge 30-day-old objects. Verify
   `mc ilm ls local/import-export`.
5. Expand the PVC: `kubectl -n gp-data edit pvc
   data-minio-0`.

### 6. Replication lag — `<runbook:s3#replication-lag>`

`S3ReplicationLagHigh` (1 GiB) /
`S3ReplicationLagCritical` (10 GiB) fired (SaaS only).

1. `kubectl -n gp-data exec -it minio-0 -- mc admin
   replicate status` — show the replication state.
2. Check the replica region (default: `ap-southeast-2`).
3. If the replica is down, bring it up via the
   `kubectl apply -f backup-cluster.yaml` workflow.
4. RPO ≤ 15 min is the canonical SLO; if the lag
   exceeds 1 GiB for > 15 min, escalate to the
   platform-primary on-call.

### 7. Bucket-init Job failed — `<runbook:s3#bootstrap-failed>`

`S3BootstrapJobFailed` fired.

1. `kubectl -n gp-data logs job/storage-bucket-init`
   — identify the failing `mc` call.
2. The Job is idempotent: re-run with
   `kubectl -n gp-data create job --from=job/storage-bucket-init
   storage-bucket-init-restart`.
3. If the failure is `connection refused`, the
   MinIO pod is not yet Ready. The Job retries
   automatically.
4. If the failure is `AccessDenied`, the IAM
   binding for the `storage-bucket-init` SA is
   missing. Re-run the chart.

## Backup + restore

The MinIO cluster is backed up via the
`backups.minio` CronJob (umbrella chart). The
schedule + destination are configured in
`values.yaml`. Restore is a controlled process:

1. `mc mirror --overwrite backup/ media/` —
   restore the `media` bucket from the latest
   snapshot.
2. `mc mirror --overwrite backup/ import-export/`
   — restore the `import-export` bucket.
3. For the `dna-raw` bucket: restore from a
   legal-hold-aware snapshot. The `dna-raw` bucket
   is object-locked; the restore MUST preserve
   the compliance mode.
4. Validate the restore with `mc ls --recursive
   local/<bucket>` + checksum diff against the
   source snapshot.

## Compatibility test

`scripts/check-s3-compatibility.mjs` runs the E2.7
contract test. The test exercises every
`required: true` S3 API operation on both providers
(AWS S3 mocked + MinIO Testcontainer) and asserts
the parity invariants. The test is wired into
`pnpm test:contract` + `pnpm check:platform`.
